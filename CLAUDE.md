# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this branch is

You are on the **`manifest`** branch — a long-lived **orphan** branch of `zackees/soldr` that shares **no history** with `main`. There is no Rust crate, no Python package, no build, no test suite here. The tree is a public, content-addressable catalogue of third-party tool releases that soldr CI consumes. All real source code (including the generator script) lives on `main`.

If you find yourself wanting to run `cargo build`, `pytest`, `npm install`, etc., you are on the wrong branch. Switch to `main`.

## What lives here

```
/manifest.json                    # top-level index: tool name -> per-tool manifest path
/<tool>/manifest.json             # one per GitHub-Releases-backed tool
    cargo-chef, cargo-xwin, cargo-zigbuild, crgx, zccache
/deps/<tool>/manifest.json        # one per vendored SDK (no upstream GH release)
    deps/mac/, deps/python/, deps/win/node/
/deps/<target>/<tool>/<version>/  # LFS-tracked binary archives (the actual bytes)
    e.g. deps/x86_64-pc-windows-msvc/cargo-chef/0.1.73/*.tar.zst
/asset-index.json                 # flat global index: every tracked asset + sha256
/README.md                        # human-facing description
```

Untracked workspace cruft (`src/`, `target/`, `examples/`, `.venv/`, `uv.lock`, `.extern-repos/`, `.github/`) is leftover from a `main` checkout sharing this working directory — none of it is part of the branch tree. Confirm with `git ls-tree -r HEAD --name-only` before assuming a file is part of this branch.

## The two manifest shapes (schema v5)

**GitHub-Releases tools** (`<tool>/manifest.json`) — flat JSON array of self-describing release dicts, newest first by `published_at`. Each entry carries `tool`, `owner`, `repo`, `tag`, `version`, `platforms` (normalized `os-arch[-extra]` keyed view, the consumer entry point), and `assets` (raw upstream filename keyed view, kept for back-compat).

**Vendored SDKs** (`deps/<tool>/manifest.json`) — single object with `kind: "vendored-sdk"`, `releases: { <tag>: {...} }`, where each platform entry has `filename`, `asset` (path in this branch), `url` (`media.githubusercontent.com` LFS URL), `size`, and `sha256`.

The top-level `/manifest.json` is a thin index (`tools.<name>.{path, owner, repo, latest, pinned, tracked_tags}`) — no asset URLs at the top level.

The README example shows schema v3 (releases as a keyed object). The actual on-disk format is v5 (flat array). Trust the files, not the README, when they disagree — and prefer `head` of one of the real files when you need the current shape.

## Git LFS

`.gitattributes` puts every `deps/**/*.{tar.zst,tar.zstd,tar.xz,tar.gz,zip}` under Git LFS. Consumer URLs in the manifests therefore point at `https://media.githubusercontent.com/media/zackees/soldr/manifest/...`, **not** `raw.githubusercontent.com`. If you generate a new vendored-SDK URL, use the `media.` host or downloads will return an LFS pointer file instead of the archive. Have `git lfs install` configured before committing or fetching LFS-tracked files.

## Editing rules (specific to this branch)

- **Do not hand-edit `<tool>/manifest.json`, `deps/<tool>/manifest.json`, `/manifest.json`, or `asset-index.json`.** They are generated by `.github/scripts/build_manifest.py` and `build_asset_index.py` (both on `main`). If something is wrong, fix the generator on `main`, then run the refresh workflow.
- **Refresh path:** `.github/workflows/refresh-manifest.yml` on `main` runs the script, content-compares, and commits any diff back to this branch. Manual refresh — from a `main` checkout with the script in it:
  ```sh
  GITHUB_TOKEN=$(gh auth token) \
    python3 /path/to/main/.github/scripts/build_manifest.py \
      --output-dir . --repo-root /path/to/main
  ```
- **Adding a vendored archive:** stage the binary at `deps/<target>/<tool>/<version>/<filename>` (will be picked up by LFS via `.gitattributes`), update the relevant `deps/<tool>/manifest.json`, and let the generator on `main` refresh `asset-index.json`. Verify the `sha256` matches the actual file bytes — downstream consumers depend on this for trust.
- **Commit message convention** matches existing history: `manifest: <imperative description>` (e.g. `manifest: vendor Node Windows SDK bundles`, `manifest: nightly refresh (YYYY-MM-DD)`).

## Hands off the orphan history

**Do not rebase, force-push, or merge `main` into this branch** — even if a tool nags you to. The whole content-addressable trust contract depends on commits never being rewritten: downstream CI hashes a file here and trusts it for as long as that commit stays on the branch. Rewriting history breaks every downstream consumer that pinned a SHA. This applies even to "fixup" commits — make a new commit forward.

## Platform key shape (for any new entries you add)

```
os    ∈ { linux, darwin, windows }
arch  ∈ { x64, arm64, universal2 }
extra ∈ { gnu, musl, msvc, gnullvm, ... }     # only when meaningful
```

Modern arch names (`x64` not `x86_64`, `arm64` not `aarch64`) — npm/Node.js convention. 32-bit binaries (i686 / armv7) are not surfaced; do not add them. Debug/symbol assets (names containing `-debug`, `.debug`, `-sym`, or `.pdb`) go in the raw `assets` map only, never in the consumer-facing `platforms` map.
